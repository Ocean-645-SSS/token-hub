## 面试前 10 分钟：先记住这十句话

1. 用户买的是平台内、按模型区分的 Token 使用额度；API Key 是调用凭证，不是买到的商品。
2. 普通购买同步建单；秒杀 Redis 预占后通过 MQ 异步建单。两者支付后都通过 MQ 发放 Token。
3. 秒杀 SUCCESS 只代表订单创建成功、可去支付；不是支付完成，也不是订单状态 COMPLETED。
4. Outbox 是 MySQL 的 local_message 表；Publisher 是应用后台发布逻辑；Broker 是 RabbitMQ；Consumer 是应用消费逻辑。
5. Publisher confirm 确认 Broker 接收；Consumer ACK 确认消费处理。两种确认不能混为一谈。
6. 消息可以重复，业务效果需要幂等：数据库唯一约束、条件状态更新、账本业务标识和 Lua 各自保护不同边界。
7. Wallet 和 Ledger 都是 MySQL 表：前者是余额快照，后者是变更流水。Redis 保存模型调用期间的热余额与冻结记录。
8. 商品库存预占和模型 Token 额度冻结不是同一件事；冻结不等于实际消费。
9. MySQL 是套餐交易事实源；ES 是搜索投影；LLM 负责解释需求和候选，不能决定库存、价格或记账。
10. 性能 bullet 报告的是两个阶段的服务端分段 P99 改善。100 并发不是 100 QPS，100 单建单成功不是 100 单已支付到账。

## 一、项目介绍与整体架构

### Q01｜请用一分钟介绍 TokenHub。【必背】

**主答：**TokenHub 是面向 AI 开发者的模型 Token 交易与调用平台。用户可以普通购买或参加秒杀，支付后平台异步把额度发到对应模型的钱包，之后用平台 API Key 调模型，按上游真实 usage 扣额度。项目用 Spring Boot 单体承载业务，MySQL 保存订单和账务，Redis Lua 做秒杀预占与额度冻结，RabbitMQ 连接异步建单和履约，ES 与 LLM 完成套餐搜索和导购。我准备重点展开四件事：两种购买链路的差异、异步消息的幂等、调用前后额度如何变化，以及如何通过分段压测定位排队延迟。

**追问 1：为什么不拆微服务？**

答：当前规模和演示目标下，单体能把事务边界、库存和账务讲清楚，也便于复现。拆服务会增加网络故障和分布式一致性成本，没有证据表明当前需要。代码按 Controller、Service、Mapper 和 messaging 分层，先把业务边界保持清楚。

**追问 2：技术版本和项目范围是什么？**

答：当前 pom 是 Java 17、Spring Boot 3.3.13；旧设计里的 JDK 21 是目标，不是当前构建事实。V1 使用模拟支付、单 Provider、非流式调用，没有真实支付、退款、微服务或多 Agent。

### Q02｜用户到底购买了什么？套餐库存、Token 和 API Key 有什么关系？

**主答：**套餐库存的单位是“份”，每份包含某个模型的若干 Token 额度。买一份会占用一份商品库存，支付履约后给该模型钱包增加额度。API Key 只是访问平台模型接口的凭证；上游厂商 Key 由平台保管，不出售给用户。JWT 用于平台业务登录，平台 API Key 用于模型调用鉴权。

**追问 1：不同模型额度能共用吗？**

答：V1 按 userId + modelCode 分钱包，不做统一 Credits 换算。这样购买和消费都能对应具体模型，避免引入跨模型兑换规则。

**追问 2：API Key 与 Idempotency-Key 有什么区别？【反复问过】**

答：API Key 回答“你是谁、能调用什么”；Idempotency-Key 回答“这是哪一次业务请求”。同一次调用因网络问题重发应复用幂等键，不能把 API Key 当作每次请求的业务编号。

## 二、普通购买与秒杀：把共同阶段合起来记

### Q03｜完整比较普通购买和秒杀链路。【必背·反复问过】

**主答：**两条链路的差异主要在建单前，建单后的支付、额度发放、超时和回补基本共用。

| 阶段 | 普通购买 | 秒杀 |
| --- | --- | --- |
| 入口 | JWT + packageId + 购买幂等键 | JWT + activityId，服务端生成 requestId |
| 库存 | MySQL token_package.stock 条件扣减 | 活动前预热独立库存，Redis Lua 原子预扣 |
| 建单 | MySQL 事务同步创建 WAIT_PAY | 写 SECKILL_ORDER Outbox，经 MQ 异步创建 WAIT_PAY |
| 首次返回 | 待支付订单 | requestId + QUEUING |
| 超时安排 | 建单事务写 ORDER_TIMEOUT | 建单事务同样写 ORDER_TIMEOUT |
| 支付 | WAIT_PAY → PAID，同事务写 TOKEN_GRANT | 相同 |
| 履约 | MQ → 唯一流水 + Wallet 增额 → COMPLETED | 相同 |
| 取消/超时回补 | MQ 异步回补 MySQL 普通库存 | MQ 异步回补 Redis 秒杀库存，保留参与记录 |

可以口述成：普通链路是“数据库先建单，再支付，再 MQ 发额度”；秒杀链路是“Redis 先拿资格，再 MQ 建单，再支付，再 MQ 发额度”。

**追问 1：普通购买用了 MySQL 事务，为什么还要 MQ？【反复问过】**

答：事务解决当前数据库操作一起成功或失败；MQ 解决后续工作异步执行。普通建单本身同步完成，但支付后的发放、超时检查、取消回补仍经过 MQ，两者不冲突。

**追问 2：什么时候用户真正拿到 Token？**

答：不是抢到资格，也不是 WAIT_PAY，更不是支付接口一返回就一定到账。发放消费者成功提交 Wallet、Ledger 和完成状态后，才算这笔购买履约完成。

**追问 3：秒杀支付时还会再扣一次 MySQL 秒杀库存吗？**

答：当前实现不会。seckill_activity.stock 用于活动初始库存，实时秒杀扣减和取消回补在 Redis；普通库存与秒杀库存独立，不能按同一份库存重复扣。

### Q04｜普通购买怎样防超卖与重复下单？

**主答：**插订单、带 stock > 0 和有效状态条件的库存扣减、写超时 Outbox 在一个 MySQL 事务内。扣库存影响行数不是 1 就抛异常，整笔事务回滚。同一次购买按 userId + purchaseKey 唯一约束；入口先查是快速返回，真正挡住并发重复的是数据库唯一键。

**追问 1：两个请求都先查到“没有订单”怎么办？**

答：让数据库唯一约束裁决。重复插入的一方事务回滚后，外层 NormalOrderPurchaseService 再查询胜出的订单并返回。不能只依赖先查询，也不能在已失败的事务里继续拼后续业务。

**追问 2：同一用户能再次购买同一套餐吗？**

答：能，主动复购换新 purchaseKey；网络重试复用旧键。相同用户同键但换 packageId，返回 IDEMPOTENCY_KEY_CONFLICT。每次重复点击都换键，会被当成不同购买。

### Q05｜Redis Lua 秒杀具体原子做了什么？

**主答：**检查活动存在和启用、活动时间、用户是否参与、库存是否足够；满足后库存减一、用户加入参与集合，并写 PENDING 预占记录。把这些 Redis 操作放进同一脚本，避免“检查时有库存，扣减时已被别人拿走”和同用户并发重复预占。

**追问 1：为什么不用普通 GET 后再 DECR？**

答：两次独立命令之间可能插入其他请求，多个请求可能同时读到最后一份库存。Lua 将检查与修改串在同一个 Redis 执行过程里。其原子范围只是 Redis，不包含后面的 MySQL 和 RabbitMQ。

**追问 2：既然 Redis 防过重复，数据库为什么还有唯一键？**

答：入口重复与消息重复是不同问题。MQ 可能重投，多个消费者也可能并发，所以 orders.request_id 和 (user_id, seckill_activity_id) 还要唯一，保护最终落库。

**追问 3：Redis 不可用时直接回源 MySQL 秒杀可以吗？**

答：当前秒杀快速失败，不把所有突发流量转到数据库。设计新的数据库降级链路还要保证库存口径与并发能力，不能把“回源”当成无成本兜底。

### Q06｜QUEUING、SENDING、SENT、WAIT_PAY 是同一个状态机吗？【反复问过】

**主答：**不是，要先说状态属于谁。

| 对象 | 典型状态 | 含义 |
| --- | --- | --- |
| 客户端秒杀查询结果 | QUEUING / SUCCESS:orderNo / FAILED | 用户目前能看到的受理结果 |
| MySQL Outbox 普通发送流程 | PENDING(0) → SENDING(3) → SENT(1)，失败转 2 | 消息待领取、已认领、Broker 确认；不是消费进度 |
| Redis 秒杀预占 | PENDING / SENT / ORDER_CREATED / FAILED | 资格与异步建单进展，按当前源码口径 |
| MySQL 订单 | WAIT_PAY / PAID / GRANTING / GRANTED / COMPLETED 等 | 支付履约的业务状态 |

**追问 1：SENT 是消息已经到 Consumer 并处理完吗？**

答：常规 Outbox SENT 只表示 Broker 确认，并不证明 Consumer 已执行。Redis ORDER_CREATED 才对应订单创建并发布结果；订单 COMPLETED 则还要支付和发放完成。

**追问 2：为什么资料里还写 RELEASED？**

答：旧设计列过 RELEASED，但当前预占失败补偿 Lua 写的是 FAILED，消费者只接受 PENDING/SENT。面试描述现实现应以源码为准。还要注意 stock.release 是特殊事件：Outbox 完成由消费者确认，不能把所有事件的 SENT 都一概解释成仅发布完成。

### Q07｜Redis 预扣成功，Outbox 写失败怎么办？

**主答：**这是跨系统的一致性窗口，单个 MySQL 事务覆盖不了 Redis。当前入口捕获写事件失败，执行补偿 Lua：仅对 PENDING 预占、且首次创建补偿标记时回补库存，再把预占改为 FAILED。消费者只处理 PENDING/SENT，可拦住已经失败的预占消息。

**追问 1：如果补偿时 Redis 也挂了，或者进程在预扣后崩溃呢？**

答：当前补偿是尽力执行，源码没有完整的秒杀预占定时对账闭环，不能承诺所有崩溃窗口自动恢复。后续需要持久化预占意图/恢复任务，按 requestId 关联订单与事件后补发或释放，并通过故障注入验证。

**追问 2：检查了状态，能保证迟到消息绝不建单吗？**

答：能挡住读取时已经 FAILED 的消息，但“读预占状态”和“MySQL 提交建单”不是跨系统原子操作，极端并发竞态仍需状态认领、恢复协议或其他协调设计。不能把设计目标说成已完成的严格证明。

### Q08｜支付、取消、超时同时发生，如何决定谁赢？

**主答：**三个动作都以 WAIT_PAY 为前置条件，SQL 更新携带旧状态，只有影响行数为 1 才获得后续动作资格。支付成功的一方写 TOKEN_GRANT；取消或超时成功的一方写对应库存释放事件。状态修改和事件在同一个 MySQL 事务提交。

**追问 1：affectedRows == 1 说明 Token 发放完成了吗？**

答：只说明本次状态迁移成功，可以创建后续事件；异步副作用是否完成，还要看消费者的事务结果。支付成功与履约成功分开。

**追问 2：为什么不在 Java 里先判断状态再普通 UPDATE？**

答：先查后改之间有竞争窗口。必须把旧状态条件放到更新 SQL 里，数据库才能让并发竞争只有一个合法结果。

### Q09｜15 分钟超时关闭如何实现？

**主答：**建单事务写 ORDER_TIMEOUT，Publisher 用 order.delay 路由到 order.delay.queue，队列 TTL 为 900000ms。过期消息经死信路由 order.timeout 进入 order.timeout.queue，由消费者检查并条件关闭 WAIT_PAY 订单，再写库存回补事件。

**追问 1：order.delay 和 order.timeout 是两次独立业务吗？**

答：它们是同一超时检查的两个阶段：先等待，再检查。当前是否能关闭主要由数据库 WAIT_PAY 条件决定；源码没有额外比较订单应付截止时间，expired_at 在超时关闭时写入当前时间。已支付订单不会被再次关闭，不能把“已校验独立到期时间”说成现实现。

**追问 2：能保证下单后第 15 分钟整被关闭吗？**

答：不能。Outbox 发布延迟、队列和消费者排队都会让检查滞后，且队列 TTL 从入队计时。当前方案是延迟检查机制，不是精确定时器；若需要更严格关闭时限，可新增明确的支付截止时间并增加扫描补偿，但不要说当前已经有这条订单扫描兜底。

### Q10｜普通和秒杀取消回补有哪些共同点和不同点？【反复问过】

**主答：**共同流程是“条件关闭订单 → 同事务写释放事件 → MQ → 消费者按订单类型回补”。普通订单回补 MySQL 库存，事件完成与库存增加可以处于同一事务；秒杀回补 Redis，先用 Lua 幂等加库存，再确认 MySQL 事件。

**追问 1：普通回补为什么可以先标记事件，再加库存？**

答：两步在一个数据库事务里。只有事件条件更新成功的一方能加库存；库存 SQL 抛异常则整笔回滚，不会只留下“已完成”标记。并发重复消息更新不到事件就不再加库存。

**追问 2：秒杀 Redis 已加库存，但 MySQL 标记失败怎么办？**

答：Lua 用 release:orderNo 作为幂等标记，首次设置成功才加库存。重试时标记已经存在，不再加库存，只补确认事件。这里没有 Redis 和 MySQL 的分布式事务，而是副作用幂等后允许重试。

**追问 3：回补后，这个用户能重新抢吗？**

答：不能。库存占用与活动参与资格分开；seckill:users 中保留参与记录。释放的一份库存给其他尚未参与的用户，不是恢复原用户的再次参与资格。

### Q11｜requestId、orderNo、messageId、bizId 分别负责什么？【反复问过】

**主答：**requestId 关联一次秒杀预占，或在模型调用中存调用幂等键；orderNo 标识订单；messageId 标识一条消息记录和确认关联；bizId 标识具体业务效果。同一次业务重投，业务标识必须稳定，不能每次重试生成新 bizId。

**追问 1：给一个完整例子。**

答：秒杀 requestId=R1 创建订单 O1；SECKILL_ORDER 事件的 bizId 是 R1。O1 支付后，TOKEN_GRANT 事件的 bizId 是 O1，账本流水 bizId 是 TOKEN_GRANT_ORDER_O1。同一订单的事件与流水使用不同命名规则，不能认为所有表里 bizId 字符串都相同。

**追问 2：数据库主键 id 不也唯一，为什么还要 bizId？**

答：自增 id 只保证行不同，重试插入仍能获得新 id；稳定业务唯一键才能识别“同一笔业务又来了”。Ledger 的唯一 bizId 约束的是业务重复，而不是行号重复。

## 三、MQ 与 Outbox：面试官最容易连续追问的一组

### Q12｜为什么需要 Outbox？只发 MQ 不行吗？【必背·反复问过】

**主答：**支付数据库事务与 MQ 发送不能天然一起提交。如果先改订单再发消息，进程可能在中间崩溃；先发消息再提交订单，消费者可能处理一个最终回滚的支付。因此我把订单状态和待发事件写入同一个 MySQL 事务，Publisher 后续扫描发布。Outbox 是把“后续还必须做什么”先可靠保存下来。

**追问 1：Outbox 会让消息恰好发送一次吗？**

答：不会。Broker 已收但发布方没记成功时仍会重投；所以采用可重试投递加业务幂等，追求同一业务效果不重复，不声称 MQ 恰好一次。

**追问 2：既然要落 Outbox，秒杀不是仍然写 MySQL 吗？**

答：是。Redis 提前过滤无库存和重复参与的请求，成功预占仍要写本地消息，建单也最终落库。收益是缩短入口工作、削峰和解耦，不是“秒杀完全不碰数据库”。

### Q13｜Publisher、Broker、Exchange、Queue、Consumer 怎么串起来？

**主答：**Publisher 是应用中扫描 local_message 并发送的组件；Broker 是 RabbitMQ 服务。消息先到 Exchange，按 routing key 与绑定规则进入 Queue，Consumer 订阅队列执行 Java 业务逻辑。当前主 Exchange 是 durable DirectExchange：tokenhub.events；topic 字段里存的是路由键，不代表用 TopicExchange。

**追问 1：项目有哪些 routing key，它们有什么逻辑关系？【反复问过】**

答：主 Exchange 有六个：seckill.order 异步建单、token.grant 支付后发放、order.delay 等待超时、order.timeout 执行超时检查、stock.release 关闭后回补、package.index 更新搜索投影。另外 tokenhub.dead 的 package.index.failed 路由到 package.index.dlq。它们不是每单都必须走完的流水线，支付和关闭是不同分支。

**追问 2：待支付对应哪条 MQ 消息？**

答：WAIT_PAY 是订单状态，不是独立 routing key。建单时写 order.delay 是安排未来超时检查；不能把“待支付状态”当成一个消费队列。

### Q14｜Publisher confirm 与 Consumer ACK 有什么区别？【反复问过】

**主答：**confirm 面向发布方，表示 Broker 对发布作出确认；ACK 面向消费交付，表示消费者处理结果。得到 confirm 不等于建单完成。项目发布方使用 correlated confirm，并检查 returned message；消费端使用 Spring AMQP AUTO，由容器在 listener 成功返回后确认。

**追问 1：AUTO 是收到消息就立即 ACK 吗？**

答：这里指 Spring AMQP 容器的 AUTO，不是 RabbitMQ 协议的 autoAck=true。当前 listener 正常返回后容器才确认；如果把业务异步扔给另一线程后立即返回，就会破坏这个完成边界，当前不能这样随意改。

**追问 2：confirm ACK 了为什么还要检查 Return？**

答：消息可能到达 Exchange，却没有路由到队列。项目开启 mandatory 和 publisher-returns，结合 confirm.isAck 与 correlation.getReturned() 判断发送结果，不能只看 ACK。

### Q15｜Outbox 的 claim、in-flight 和失败恢复怎么做？

**主答：**Publisher 查询到待发消息后，用条件 UPDATE 把 0/2 改成 3（SENDING），只有领取成功才发。Semaphore 限制同时在发送或等待收尾的消息数，当前默认上限 1000。成功确认后改为 1；发送异常、NACK 或 Return 转入重试并设置 next_retry_time。定时回收长期 SENDING，避免进程崩溃后一直无人处理。

**追问 1：batchSize、in-flight、线程池线程数是一回事吗？**

答：不是。batchSize 限制一轮最多查询多少条；in-flight 限制未收尾消息总量；线程数限制同时执行发送任务的 worker 数；线程池队列限制等待执行的任务数。当前领取还受线程池可接收容量约束。

**追问 2：线程池满了，消息是不是就丢了？**

答：当前使用有界队列和 AbortPolicy，拒绝会被捕获，已领取消息退回重试状态，并释放许可、记录指标。不能静默丢任务，也不能误把尚未发送的消息标成成功。

**追问 3：超时 claim 回收能证明绝无重复、绝不泄漏吗？**

答：不能。旧发送可能只是慢，所以回收后仍可能重复发送，消费者必须幂等；数据库状态恢复也不等于内存 Semaphore 或迟到回调一定正确。当前缺少完整的真实崩溃与极端回调故障验证，后续可补 claim 代次、确认超时与故障注入。

### Q16｜消息重复、消费失败和顺序错乱分别怎样处理？

**主答：**重复由业务幂等处理：建单唯一键、订单条件迁移、购买发放唯一账本和库存回补标记。异常不能在业务未完成时被吞掉并正常返回，否则会被当作成功 ACK。顺序上不依赖全局 FIFO，而是通过当前业务状态判断这条消息还能不能生效。

**追问 1：消费者事务已经提交，ACK 前宕机怎么办？**

答：可能重新投递。建单按 requestId 查已有订单；发放按订单和唯一流水防止再加余额；回补按事件状态或 Lua 标记防止再加库存。

**追问 2：所有队列都有三次重试后 DLQ 吗？**

答：不能这样说。源码明确给 package.index 做了最多三次尝试与 DLQ；其他队列不能套用它的策略。要按实际 listener、容器错误处理和队列死信配置分别判断，生产完善方向是分类重试、退避和可观测的失败处置。

### Q17｜ready、unacked、prefetch 和 Consumer 并发怎么理解？【反复问过】

**主答：**ready 是还在队列里等交付的消息；unacked 是已交给消费者但还未确认的消息，其中可以有尚未进入业务方法的等待。prefetch 限制每个 Consumer 可持有的未确认消息数量，不是一次必取的数量，也不是业务线程数。

**追问 1：一个 Consumer、prefetch=250、100 条消息会同时执行吗？**

答：不会因为 prefetch 大就产生 100 个业务线程。消息可能被提前拿到消费者侧排队，所以 ready 低但 unacked 上升，仍可能很慢。

**追问 2：4 个 Consumer、prefetch=32，是全队列最多 32 条吗？**

答：在本项目这种非 global 的配置下，每个 Consumer 各有上限；4 个约可持有 128 条未确认消息，但实际数量受流量和处理速度影响。配置 4–8 是初始和最大消费者数，不代表一直恰好 8 个。

### Q18｜哪些操作用 Lua，哪些不用？【反复问过】

**主答：**当前 Lua 主要有八类：秒杀资格和库存预占、秒杀入口失败补偿、确认后条件标记 SENT、取消后的秒杀库存回补、模型额度冻结、模型额度释放、模型额度结算、API Key 固定窗口限流。其中四个秒杀脚本是资源文件，模型和限流脚本嵌在 Java 中。

**追问 1：锁钱包、写 Ledger、购买发放也是 Lua 吗？**

答：不是。它们由 Java Service 调 MySQL，在事务里用 SELECT FOR UPDATE、唯一键和 UPDATE 完成。Lua 不能锁 MySQL 行，也不能让 MySQL 与 Redis 一起提交。

**追问 2：有 Lua 就不需要数据库事务了吗？**

答：Lua 管 Redis 内操作不被其他命令插入；数据库事务管本地数据库提交与回滚。两个保护范围不同，跨系统仍需要幂等、补偿与恢复。

### Q19｜什么是削峰？MQ 会自动提升吞吐吗？

**主答：**削峰是把短时间到来的请求先排队，让下游按可承受速度处理。MQ 可以平滑建单写入，也让接口早返回受理状态，但不凭空增加数据库处理能力；如果长期入队速度高于消费速度，积压和完成延迟仍会增加。

**追问 1：多开 Consumer 不就解决了吗？**

答：还要看数据库连接、锁竞争、CPU 和下游容量。当前 Consumer 优化后已经出现 Hikari 等待和事务耗时增加信号，所以扩并发要结合观测，不能无限加。

**追问 2：RabbitMQ 为什么适合这里，不用 Kafka？**

答：本项目需要按业务队列投递、确认、重试和 TTL/DLX 延迟检查，RabbitMQ 能直接表达这些需求。没有做 Kafka 对照压测，所以不说 RabbitMQ 一定更快；这是围绕当前工作流和复杂度的选择。

## 四、Token 账户与计费：先分清“购买入账”和“调用扣费”

### Q20｜Wallet、Ledger、model_request 三张表分别做什么？【必背·反复问过】

**主答：**Wallet 是每个用户每种模型的余额快照，包含 available_token、frozen_token、credit_limit；Ledger 是购买和消费的变更明细，包含 bizId、正负 amount 和变更前后余额；model_request 记录某次模型调用的状态、预冻结量、真实 usage、重试次数与结果引用。三张都是 MySQL 表，各有分工。

**追问 1：冻结 2000 就写一条消费 2000 的 Ledger 吗？**

答：不写。冻结只是占用额度，真实消费要等上游 usage；如果用了 1500，最终消费流水是 -1500，多冻结的 500 释放。

**追问 2：Wallet 的 version 字段就是乐观锁吗？**

答：不能只凭字段名判断。当前 Mapper 会递增 version，但更新 SQL 没有 WHERE version=旧版本 的比较条件；购买发放的互斥主要靠事务中的 FOR UPDATE，不应说已经用版本号完成了乐观锁重试。

### Q21｜支付后如何发放 Token，并防止重复发放？【反复问过】

**主答：**支付事务把 WAIT_PAY 改成 PAID，同时写 TOKEN_GRANT Outbox。Publisher 发到 token.grant.queue，Consumer 调用 TokenGrantHandler。Handler 在事务里检查订单状态、推进到 GRANTING、创建或锁定对应钱包，尝试插入 TOKEN_GRANT_ORDER_订单号 流水，只有 insertIgnore 返回 1 才加余额，再推进 GRANTED 和 COMPLETED。

**追问 1：为什么先插流水再改 Wallet？是因为只有流水在数据库吗？**

答：不是，二者都在数据库。先通过唯一流水判断本次是否第一次产生业务效果，只有首次插入才更新钱包；两步在同一事务，因此不会允许“流水提交了、余额没提交”的部分成功。

**追问 2：状态机和 bizId 谁负责防重？**

答：状态机限制流程合法性，唯一 bizId 限制同一业务记账一次，钱包行锁协调同一账户并发。它们保护不同层次，不能只保留其中一个就认为所有重复与竞争都解决了。

### Q22｜SELECT FOR UPDATE 到底锁什么？【反复问过】

**主答：**项目按 (user_id, model_code) 唯一条件查询钱包并加 FOR UPDATE，在有效数据库事务里锁定匹配钱包记录，直到提交或回滚。其他并发更新同一钱包需要等待，避免同时读出旧余额后互相覆盖；不同钱包可以独立处理。

**追问 1：只写 FOR UPDATE，不开启事务也有用吗？**

答：不能把它当作覆盖整个 Java 方法的锁。自动提交时语句结束锁就释放，后续更新不受这次读锁持续保护；因此必须核对调用是否真的进入 Spring 事务，不能只看 SQL。

**追问 2：能不能把外部模型 HTTP 调用也放进钱包锁里？**

答：不适合。上游可能等待很久，会长期占连接和锁。应先短事务记录请求与额度预留，调用上游不持数据库锁，返回后再短事务结算，并用状态和恢复机制衔接。

### Q23｜为什么要预冻结？完整计费链路怎么走？

**主答：**调用前不知道真实 usage，如果只查余额就放行，多条并发请求会重复使用同一份额度。因此先按“估算输入 + maxOutputTokens + safetyMargin”冻结，再请求上游；成功拿到真实 usage 后只扣实际量并释放差额，最终失败释放全部冻结。预冻结是并发保护，Ledger 的最终消费依据是真实 usage。

**追问 1：给一个数字例子。**

答：原可用 10000、冻结 0；预冻结 2000 后变为可用 8000、冻结 2000。实际用 1500，结算后可用 8500、冻结 0，写消费 -1500。若请求彻底失败，恢复可用 10000、冻结 0。

**追问 2：输入 Token 怎么估算？准确吗？**

答：当前代码按字符数约除以 4 的粗估值，加最大输出和安全余量，不是逐模型精确 tokenizer。它用于保守预留，不当作收费依据。中文、特殊内容等可能偏差，所以要区分估算与实际 usage。

### Q24｜如果实际 usage 超过冻结量，怎么办？

**主答：**设计允许固定 5000 Token 信用额度。预冻结若会使可用余额低于 -5000，就拒绝，不调用模型。真实 usage 返回后仍按实际量结算；若补扣使余额突破信用下限，记录真实消费并暂停账户，阻止后续调用。

**追问 1：冻结不够就直接把超出的成本忽略吗？**

答：不能。冻结是预估，不是费用上限。真实消费已发生时要记录真实 usage，再执行信用与暂停规则，而不是伪造用量。

**追问 2：预冻结失败也会暂停账户吗？**

答：当前不会因为这次预冻结失败直接 suspend；只是拒绝此次调用并把请求标 FAILED。与上游成功后真实消费突破信用下限的场景不同。

### Q25｜模型请求如何幂等？重复扣费仅靠 bizId 吗？【反复问过】

**主答：**当前把请求头 Idempotency-Key 存到 model_request.request_id，用唯一约束抢占执行资格。已有 SUCCESS 就返回保存结果；PROCESSING 返回处理中；FAILED 要求换新 Key；BILLING_UNKNOWN 保留未知计费语义。它优先阻止同一次请求重复调用上游。Ledger 另用 MODEL_CONSUME_请求标识，但当前结算先改余额再 insertIgnore，未检查插入结果，因此不能声称单靠流水唯一键就保证重复结算安全。

**追问 1：客户端超时，服务器其实已结算成功怎么办？**

答：客户端重试复用原 Key，查到 SUCCESS 后返回原结果，不再调用或扣费。计费成功不以客户端最后有没有收到 HTTP 响应为准。

**追问 2：上次冻结失败，继续用同一 Key 能再试吗？**

答：当前记录已是 FAILED，同 Key 返回 IDEMPOTENCY_KEY_REUSE，需要新 Key。不要把“网络不确定时用原 Key 查询结果”和“已明确失败后重新发起”混起来。

**追问 3：这个幂等实现还缺什么？**

答：当前查询按全局 request_id，读取已有结果没有核对所属用户与请求内容摘要。完善时应限定 userId/API Key 作用域并保存请求指纹；同键不同参数返回冲突。这是待改进，不要说当前已经具备跨用户隔离的完整幂等协议。

### Q26｜上游失败、重试、缺 usage，各怎么计费？

**主答：**可重试的网络错误、超时及 429/502/503/504 最多三次总尝试，退避 200ms、500ms；参数、鉴权和权限等错误不应盲目重试。最终失败释放冻结，不向用户写成功消费；成功却没有 usage 时标 BILLING_UNKNOWN、释放冻结，不拿估算值收费。

**追问 1：三次尝试会扣用户三次吗？**

答：计费目标是一项业务请求只记成功结算的一次消费；失败尝试的上游成本由平台承担，不能每次失败都扣用户。当前源码没有完整逐次尝试成本账本，不应说已把每次上游成本精确核算。

**追问 2：超时是不是代表上游根本没执行？**

答：不是，也可能执行了但响应丢失。因此本地幂等只能控制平台再次处理同 Key，不能天然保证上游不重复执行；如需更强语义，要依赖上游幂等支持或可查询请求协议。

### Q27｜计费链路的实现边界是什么？如果面试官看代码，怎么答？

**主答：**已实现的是请求去重、额度预冻结/结算/释放流程、购买发放的事务幂等，以及过期冻结清理。但不能把它说成所有故障下账务强一致。当前模型结算仍有事务边界和跨存储恢复缺口，下一步应该围绕账务可恢复性完善。

**追问 1：具体哪几处不能夸大？**

答：第一，ChatCompletionService.complete 同类直接调用带 @Transactional 的 settle，默认 Spring 代理下属于 self-invocation，事务拦截不会因此生效。第二，冻结/释放服务没有统一有效事务覆盖钱包锁与更新，Redis 和 MySQL 先后成功仍可能分叉。第三，购买发放只改 MySQL Wallet，没有同步已有 Redis 热钱包，后续调用可能读到旧额度。第四，清理任务与慢调用完成之间仍需更严格的状态竞争控制。

**追问 2：你会怎么改？**

答：把数据库记账移到独立事务 Bean 或 TransactionTemplate；同事务完成条件状态迁移、唯一流水和钱包增减；用业务请求状态判定谁取得结算资格。再增加可重试的余额投影同步与对账，处理 Redis 成功但 DB 失败等窗口，并测试结算、释放和清理并发。这里是改进方案，本次只整理材料，没有修改代码。

**追问 3：简历“处理重复扣费”还能怎么解释？**

答：准确说是通过 model_request 唯一请求记录和状态分支处理同 Key 重试，避免常规入口重复调用/扣费；不把它扩张为“结算函数任意重放也绝对安全”。购买发放与调用扣费的实现强度不同，要分别解释。

## 五、ES 与 AI 导购：模型输出必须回到业务事实

### Q28｜两阶段导购怎么实现？【必背】

**主答：**第一阶段让 LLM 把自然语言转成受限 JSON 筛选意图，后端校验字段和业务合法性，再用 ES 查候选；第二阶段把候选套餐事实给 LLM 生成推荐说明。流程是“意图解析 → 校验/必要时澄清 → 检索候选 → 候选内推荐”，推荐不会直接产生交易或修改库存。

**追问 1：两阶段是不是只调用两次 API、所有请求都走满两次？**

答：不是。它描述逻辑阶段；解析重试可能多次，澄清或空候选可能提前返回，推荐失败也会走模板。不能把逻辑阶段数当成固定请求次数。

**追问 2：为什么不让 LLM 直接选套餐或写 SQL？**

答：价格、库存和可售状态必须由业务系统控制。结构化条件便于校验，ES 候选提供事实范围，避免让模型直接执行数据库查询或编造商品。模型负责表达理解和推荐文案，后端负责可信约束。

### Q29｜LLM 输出了合法 JSON，就可以直接查 ES 吗？

**主答：**还不够。当前校验允许字段集合、字符串格式、非负数值、范围上下界、预算限制等，再检查指定 modelCode 是否有 MySQL 在售套餐。格式合法与业务合法是两层校验。

**追问 1：模型编了一个格式正确但不存在的 modelCode 怎么办？【反复问过】**

答：当前已经补了从 token_package 查询在售模型的校验；找不到就返回澄清并暂停检索，不会把 modelCode 静默设为 null 放宽搜索。早期聊天“只校验格式”是修改前事实，不能再当现状。

**追问 2：可用模型要硬编码白名单吗？**

答：当前按 MySQL 在售套餐数据检查，并规范化到实际 modelCode。新增套餐后无需同步修改代码白名单；如果后续做缓存，要一起设计变更失效。

### Q30｜模型解析失败、推荐失败、空候选怎么分别处理？

**主答：**意图阶段可重试 Provider 异常会重试，结构校验失败会将校验原因交给模型修正，最多按配置三次尝试；最终失败回退原始需求关键词和显式预算。推荐阶段失败，按候选事实生成模板说明。空候选则明确没有匹配套餐，不凭空造一个。

**追问 1：用户只说“便宜一点”，是不是直接默认一个预算？**

答：若模糊约束影响筛选却无法可靠映射，返回一个具体澄清问题；普通可选字段没填不需要逐项盘问。不能替用户发明预算或悄悄改变模型偏好。

**追问 2：只在 Prompt 写“不能幻觉”，就完全安全了吗？**

答：不够。当前主要是候选约束与模板回退，不等于已经有完备的推荐文本事实校验。更强方案是让第二阶段输出候选 ID 与结构化理由，由后端验证 ID、金额和额度再渲染；这是后续增强。

### Q31｜为什么用 ES？关键词与过滤条件怎么组合？

**主答：**项目要对套餐名称、描述、场景做全文搜索，同时按模型、价格和 Token 数量过滤。ES 中文本字段用于关键词检索，modelCode 是 keyword 精确匹配，数值字段做 range，active=true 过滤下架项。MySQL 继续负责交易与事实保存。

**追问 1：不能用 MySQL LIKE 吗？**

答：小数据量当然可以。使用 ES 是为了实现全文检索和多条件搜索能力，不能在没有对照数据时说 LIKE 必然慢、ES 必然快；还要承担索引同步和运维成本。

**追问 2：这是向量 RAG 或 Agent 吗？**

答：当前没有向量库、多 Agent 或自由工具规划。它是受控的 LLM 意图解析、结构化检索和候选增强生成流程，不把框架名当成已实现能力。

### Q32｜MySQL 套餐如何同步到 ES？

**主答：**管理 API 修改套餐与写 PACKAGE_INDEX_SYNC Outbox 同事务提交，Publisher 发 package.index，消费者按 packageId 重新读 MySQL 当前事实写 ES。写入使用 catalog_version 作为 external version；启动与默认每 60 秒的全量对账另外修复索引偏差。

**追问 1：为什么消费时读 MySQL 最新数据，而不是盲信旧消息里的套餐？**

答：消息可能积压或乱序，读当前事实可减少把历史快照再写回的风险。版本保护还要保留，防止两个消费者先后读到不同版本再逆序完成。

**追问 2：数据库变更了，但 MQ/ES 暂时失败怎么办？**

答：Outbox 支持投递重试；ES 消费者有限重试后进入 DLQ；定时对账独立读取 MySQL 修复。API 返回成功不等于搜索马上可见，交易下单仍查 MySQL。

### Q33｜external version、tombstone、DLQ 各解决什么？【反复问过】

**主答：**external version 用业务版本拒绝旧写覆盖新写；tombstone 是保留版本的 active=false 文档，表示已下架，避免旧消息把商品复活；DLQ 保存消费重试耗尽的消息，便于排查和必要时重放。它们分别处理顺序、删除语义和失败处置。

**追问 1：下架后直接删 ES 文档不更简单吗？**

答：当前选择保留 tombstone 及版本，让后来的低版本写不能重新激活商品，搜索端过滤 inactive。不是把整个索引删除，也不是每次全量重建。

**追问 2：进 DLQ 后，只能人工重放才能恢复搜索吗？**

答：不一定。当前对账能在依赖恢复后按 MySQL 当前版本自动收敛，原消息可以仍留 DLQ 供排查。直接 SQL 改搜索字段也必须递增 catalog_version，否则同版本更新可能被拒绝。

### Q34｜refresh 和 60 秒全量对账有什么区别？【反复问过】

**主答：**refresh 让已经写入 ES 的变更对搜索可见；全量对账负责用 MySQL 当前事实更新 ES，修复缺失或过时状态。refresh 不读取 MySQL，也不等于重建索引。项目在同步或对账写入后显式 refresh。

**追问 1：refresh 成功就代表 MySQL 和 ES 完全一致了吗？**

答：不代表。若变更还没送到 ES，refresh 不会凭空补齐。它处理“何时可搜索”，对账处理“数据是否追上事实源”。

**追问 2：每写一条都 refresh 有没有代价？**

答：有额外搜索可见性刷新成本。当前小规模同步这样实现；量大时可评估批量写入、合适的 refresh 策略和可见性 SLA，不能把当前方式当成无限吞吐方案。

### Q35｜MySQL 有套餐，ES 因同步延迟搜不到，怎么办？【反复问过】

**主答：**先区分“没有匹配候选”和“交易时套餐已失效”。当前导购仍以 ES 候选为推荐范围，空候选不能编造推荐；保留用户条件，提示暂无匹配并等待同步/重试。下单回 MySQL 校验是另一层交易保护，不能用“付款时报错”来回答搜索缺失问题。

**追问 1：能自动去掉 modelCode 找别的模型吗？**

答：不应该擅自放宽明确条件。可以询问用户是否接受替代选项，确认后再调整检索；否则结果可能看似丰富，却不满足真实偏好。

**追问 2：推荐出来以后，价格还能变吗？**

答：搜索结果是展示信息，最终建单从 MySQL 读取套餐并记录订单价格、Token 数量快照，不能让前端或模型提交的价格直接成为成交价。支付主要基于订单状态与快照，不能笼统说“付款时重新搜索 ES”。

## 六、延迟测评与优化：从名词到完整复盘

### Q36｜第四条 bullet 用一分钟怎么讲？【必背·反复问过】

**主答：**我先区分秒杀接口返回 QUEUING 的延迟，与异步订单真正创建成功的延迟。通过 requestId 把 Outbox、Publisher、Broker confirm、Consumer 和数据库建单打点串起来，发现主要慢在两段排队。先将发送移到有界 Publisher 线程池，Outbox insert→claim P99 从 5.229 秒降到 1.316 秒；再针对秒杀队列把 Consumer 从 1 调到 4–8、prefetch 从 250 改成 32，confirm→listener P99 从 3.076 秒降到 0.361 秒。对应历史正式样本中，100 个受理请求都创建了订单，并核对了库存和重复订单。后来审计客户端脚本发现批次屏障，所以我主要报告这两段服务端改善。

**追问 1：3.076 秒和更早的 2.117 秒为什么不同？**

答：它们来自不同阶段。更早定位时 Consumer 等待 P99 约 2.117 秒；Publisher 加速后下游等待上升到 3.076 秒，这才是 Consumer 优化的 Before。不能把各轮数字任意拼成一组 A/B。

**追问 2：100/100 完成是支付到账成功吗？**

答：这条性能链路终点是秒杀异步建单成功与结果更新，不包含后续模拟支付和 Token 发放。简历的“订单正确完成”口述时应明确为“受理请求最终正确建单”。

### Q37｜并发、QPS、P95/P99、E2E 分别是什么意思？

**主答：**并发是同时在推进的请求/工作数量；QPS 是每秒请求数；吞吐还必须说明单位是 HTTP 样本还是业务订单。P95/P99 是把单笔耗时排序后的百分位边界，用于看尾部；E2E 是指定起点到终点的全流程耗时，不先定义端点就没有可比性。

**追问 1：100 并发就是每秒完成 100 单吗？**

答：不是。还取决于每单耗时、等待、脚本持续时间与循环模型。一次请求可能产生多个 HTTP 样本，也可能返回售罄或排队，所以 HTTP 吞吐不等于成功订单吞吐。

**追问 2：P99 是最慢的一笔吗？100 单够证明稳定吗？**

答：P99 是百分位，不天然等于最大值；具体取样或插值算法应保持一致。只有 100 个样本时 P99 接近样本尾部，波动较大，适合阶段定位与复测，不能推成生产容量承诺。

### Q38｜项目到底测了哪几种延迟？

**主答：**至少区分三层：POST 接口返回 QUEUING 的耗时；服务端从秒杀入口到建单提交并写成功结果的 T0→T11；客户端从 POST 开始到轮询观察到 SUCCESS 的 E2E。后者还包含客户端控制流、网络、轮询和观察延迟。

**追问 1：接口十几毫秒返回，就能说秒杀订单十几毫秒完成吗？**

答：不能。接口可能只完成资格预占与事件落库，Publisher 和 Consumer 仍在后台排队。受理快不等于履约快。

**追问 2：服务端 E2E 为什么不包含 Token 到账？**

答：这个实验测的是异步建单链路，T11 是发布订单创建结果。支付发放属于后续链路，若要测到账延迟，需要另外定义从支付开始到 Ledger/Wallet 提交的端点。

### Q39｜怎么实现“打点”，怎么算两点之间的耗时？【反复问过】

**主答：**对同一个 requestId，在进入关键阶段时记录时间戳，如 Outbox 插入后 A、Publisher claim 时 B、confirm 回调时 C、listener 入口时 D。B-A 是该请求的领取等待，D-C 是所观测的确认到监听入口区间。每条请求分别算，再对同一批样本排序统计百分位。

**追问 1：System.nanoTime 能跨 JVM 直接相减吗？**

答：不能。项目同一应用 JVM 内的相对耗时用 nanoTime；客户端与服务端关联用 requestId 和 wall-clock 毫秒，同时承认时钟与精度限制。跨机器更要考虑时钟同步，不能拿两个进程的 nanoTime 当统一时间轴。

**追问 2：全链路 P99 等于各段 P99 相加吗？**

答：不等于。每段的第 99 百分位可能来自不同请求。正确方法是先对每个请求计算全链路时长，再取全链路 P99；同一批且边界一致的平均值才适合做分段求和解释。

**追问 3：confirm→listener 就是 Broker 内纯排队时间吗？**

答：不是。它用发布确认回调与监听入口作边界，可能包含交付、客户端预取与容器排队，而且 confirm 回调与消费并非严格串行同步。要结合 ready/unacked、Consumer 数和业务阶段耗时一起归因，不能仅凭一个时间差断言 Broker 内部机制。

### Q40｜为什么判断主要慢在 Publisher 和 Consumer，而不是 MySQL？

**主答：**当轮样本里 Outbox insert→claim P99 约 5.229 秒，confirm→listener 约 2.117 秒；进入 listener 后的业务阶段远短于这两段秒级等待。再结合单 scheduler 的较长周期、单 Consumer 和预取现象，证据指向消息等待。结论限定为那轮样本，不是说数据库永远不慢。

**追问 1：ready=0，不就说明 MQ 没积压吗？**

答：只能说明采样时未交付的消息少。消息可以已经预取到 Consumer 侧、处于 unacked。结合监听入口延迟才能判断是否在消费者侧等待；单个瞬时指标不够。

**追问 2：你是看到延迟就猜瓶颈，还是有验证？**

答：先分段测量提出解释，再只改 Publisher 观察其段下降；消费端等待反而显现后，再单独调 Consumer 观察对应段下降。两次改动都核验最终订单与库存，形成“测量—假设—单组件调整—复测”的证据链。

### Q41｜Publisher 到底改了什么？【反复问过】

**主答：**把发送任务从调度线程移到专用有界线程池，core=4、max=8、queue=500。调度线程负责回收过期 claim、按容量查询、claim 和 dispatch；worker 负责发送，异步 confirm 回调收尾。保留重试、关联确认、Return 检查和预占状态条件更新。核心是拆开发送与扫描，不是把 claim 本身变成并行 SQL。

**追问 1：已经 200ms 轮询，为什么还能等 5 秒？**

答：fixedDelay 是上一轮结束后再等 200ms，不是每隔 200ms 强行新开一轮。单 scheduler 要逐条推进一批消息，一轮本身就可能持续数秒，后来的事件仍要等。也不能把异步 confirm 误讲成旧实现必然每条同步阻塞等 ACK。

**追问 2：效果与副作用是什么？**

答：对应 Publisher 实验 insert→claim P99 从 5229.020ms 到 1316.377ms，服务端 E2E 从 8011.560ms 到 4544.578ms。此时 confirm→listener 从约 2116.85ms 上升到 3076.006ms，说明发布更快后下游单消费者容量约束更明显。

**追问 3：配置 max=8，是不是平时就用 8 个线程？**

答：不是。实际线程数受核心线程、队列容量和负载影响；任务通常先由核心线程处理并进入队列，达到扩容条件才向最大数增长。要看运行指标，不凭 max 字段推断实际并发。

### Q42｜Consumer 改了什么？为什么同时降低 prefetch？【反复问过】

**主答：**只给秒杀订单队列设置专用监听容器配置，初始 4、最大 8 个 Consumer，prefetch 从 250 调到 32。增加独立订单的并行处理能力，同时减少单个 Consumer 提前占住大量未确认消息的情况。业务事务、唯一键和 AUTO ACK 边界保持。

**追问 1：取得什么结果？**

答：在 Publisher 已优化的基线上，confirm→listener P99 从 3076.006ms 降到 360.828ms；服务端 E2E 从 4544.578ms 到 1747.713ms。样本 100 个受理请求全部建单，distinct user 与 requestId 都是 100，未发现重复订单。

**追问 2：是不是越多 Consumer、越小 prefetch 越好？**

答：不是。太小可能增加交付等待，太多消费者会争抢数据库连接与锁。本轮业务事务 P99 从 25.069ms 上升到 45.604ms，并出现短时 Hikari 等待信号；说明要重新观察下游，不能继续盲调。

### Q43｜为什么服务端快了，客户端 E2E 还是约 5.4 秒？【必背·反复问过】

**主答：**后来检查压测客户端发现，它先等整批 POST Future 全部结束，才统一提交结果轮询。早完成的请求在等其他 POST，这段批次屏障也被算进单笔 E2E。因此这个数混入了脚本等待，不是纯粹的单请求完成体验。独立观测样本显示 POST response→首个 poll 平均约 4.86 秒，Result API 服务端 P99 仅约 4.421ms。

**追问 1：不是每次轮询 sleep 50ms 导致的吗？**

答：那轮 100 个请求全是第一次 GET 就看到成功，没有第二次轮询，所以 50ms sleep 没走到，不能解释秒级差距。polling executor 调度也只是毫秒级。

**追问 2：应该怎么重新测？**

答：每个请求拿到 requestId 后独立开始轮询，不等整批 POST；同时保留服务端完成时间和客户端观察时间，明确是否包含轮询间隔。用相同环境、负载、预热和 profiling 开关做新基线，不把新口径直接接到旧数字后面。

**追问 3：你已经修好这个 benchmark 了吗？**

答：该阶段只增加观测副本并完成归因，历史报告明确没有改掉原批次屏障。不能把“发现测量偏差”讲成“已完成新客户端优化并得到新收益”。

### Q44｜压测工具、实验步骤、正确性与数字边界怎么交代？

**主答：**仓库有 JMeter 的普通购买/秒杀/计费场景，但第四条 bullet 的关键分段优化主要基于 Java SeckillBenchmark、后续观测副本、服务端 profiling 日志和分析脚本。历史流程先做 10 并发预热，确认旧消息排空，再做 100 并发、100 库存、5 秒正式负载，跟踪 100 个 accepted 请求的建单完成。5 秒是负载窗口，不是承诺所有订单都在 5 秒内完成。

**追问 1：除了看接口没报错，还核验了什么？**

答：MySQL 最终订单数、distinct user 和 requestId、重复用户/活动与重复 requestId；Redis 剩余库存、参与集合、预占最终状态；Outbox 残留、发布与确认数；RabbitMQ ready/unacked 排空。HTTP 200 或 QUEUING 不能代替这些业务检查。

**追问 2：100 单样本能证明高并发系统绝对可靠、生产容量够用吗？**

答：只能证明对应本地历史样本中的行为。没有覆盖完整故障注入、长期稳定性和大规模容量；不能宣称百万请求、万级 QPS 或生产 SLA。更完整评测要扩样本、重复多轮、加入售罄/重复/慢依赖/宕机和恢复场景，并分别统计受理、拒绝与完成率。

**追问 3：两组核心数字怎样背才不串？**

答：Publisher 阶段只背“领取等待 5.229s → 1.316s”；Consumer 阶段只背“确认到监听 3.076s → 0.361s”。如果展开服务端 E2E，按阶段说约 8.012s → 4.545s → 1.748s；不要把后来的带额外 profiling 样本 1.204s 当成又一次优化结果，也不要把分段 P99 求和。

## 七、开发复盘与收尾追问

### Q45｜讲一个真实遇到的困难，如何定位和修改？

**主答：**我会讲“接口已经返回排队成功，订单却迟迟查不到”。开始只调整轮询和发布批量仍没解决到预期，随后把链路按 requestId 打点，发现时间主要在 Outbox 领取前和 listener 入口前；分两阶段改 Publisher 与 Consumer。联调后客户端数字仍不明显变化，又审计脚本发现整批 POST 屏障。沉淀的做法是先定义完成边界，再分段打点，最后检查测量工具是否把自身等待算进结果。

**追问 1：这和“把线程数调大”有什么区别？**

答：有明确的前置假设、运行证据、只改一个组件的实验和一致性验收；还能解释为什么上游变快会暴露下游瓶颈，以及为什么客户端数值不能直接宣传。

**追问 2：还有一个业务联调例子吗？**

答：导购里 modelCode 只校验格式不够，模型可能输出不存在的编码。讨论后补了 MySQL 在售模型校验，并确定“不静默去掉用户偏好，先澄清”的接口行为。这是从业务语义校准模型输出，不只是让 JSON 能解析。

### Q46｜如果继续做，你优先改什么？

**主答：**优先补账务与预占恢复的正确性，再扩性能规模。先修模型结算事务代理边界、结算/释放互斥、请求幂等作用域与 Redis 钱包同步；再补秒杀预占失败的持久化恢复和故障注入；最后用独立 per-request polling 建立新测量基线，评估连接池、数据库和更大负载。

**追问 1：为什么不是先把项目拆微服务？**

答：拆分不会自动修复账务竞态，反而扩大跨服务一致性范围。当前证据更支持先修真实缺口，做可验证的恢复协议。

**追问 2：你会怎么描述项目意义和个人收获？**

答：这个项目把库存、异步履约、账户余额和模型用量串成闭环，让我能区分“受理、发布、消费、业务完成”，也能用数据定位排队而不是凭感觉调参数。个人贡献只讲能展示源码、记录和实验的部分，不借用未证实的线上规模。
