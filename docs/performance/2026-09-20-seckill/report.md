# TokenHub 秒杀高并发性能测试报告（2026-09-20）

## 结论

- 在本机、客户端与服务端同机的条件下，秒杀**接口**最高观察吞吐为 **484.35 QPS（50 并发）**，但 P99 已从 10 并发的 42.06 ms 恶化到 475.61 ms。因此，以低尾延迟定义的当前**最大稳定 QPS 是约 420 QPS（10 并发）**，而不是峰值 484 QPS。
- 性能拐点位于 **10–50 并发**：吞吐只增加 15.3%，P99 增加约 11.3 倍。200 并发后吞吐下降；500 并发时 P99 达 4.20 s 且出现 3 个失败请求，已明确过载，故按测试约束不再盲目执行 1000 并发稳态档，补测了 300 并发定位曲线。
- 库存 100、1000 个不同签名用户并发的一致性测试中：Redis 成功预扣 100，MySQL 最终订单 100，outbox 已发送 100，RabbitMQ 秒杀队列为 0，未发现超卖、重复用户订单、重复 requestId 订单或 Redis 成功预扣未落库。
- 异步链路绝非“几十毫秒”：独立的 100 单端到端样本 P50/P95/P99 为 **5.919 s / 6.826 s / 6.912 s**。代码中的 `LocalMessagePublisher` 每 5 秒最多扫描 100 条待投递消息，是本轮最明确的最终落库延迟来源。

## A. 秒杀接口性能

此部分仅统计：客户端发起 `POST /api/seckill/{activityId}` → JWT → Redis Lua → Redis reservation 写入 → MySQL outbox 插入 → HTTP 返回 `QUEUING`。成功指 HTTP 200 且含 `requestId`。

10 并发是已测得的最佳稳定点：约 420 QPS，P95 32.41 ms、P99 42.06 ms。50 并发取得了 484.35 QPS 的瞬时峰值，但其 P99 475.61 ms，不宜称为稳定运行点。没有定义业务 SLA 的前提下，“稳定”按无错误且尾延迟未发生数量级恶化判定。

## B. 异步最终落库延迟

为避免把接口异步返回误认为订单完成，建立独立库存 100 活动，100 个不同用户均获得预扣资格；客户端从请求开始计时并轮询既有 `GET /api/seckill/result/{requestId}`，到返回 `SUCCESS:orderNo` 为止。

| Sample | Accepted | Completed | Timed out | Avg ms | P50 ms | P95 ms | P99 ms | Max ms |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 reservation → MySQL order | 100 | 100 | 0 | 5,587.64 | 5,919 | 6,826 | 6,912 | 6,913 |

同一突发样本的接口 P50 为 1,730.91 ms（该小样本含 100 个客户端线程冷启动，不能替代上表的 30 秒稳态接口结论）。端到端数据的主要信息是：全部订单最终完成，但最终落库约 5.6–6.9 秒，而非接口立即返回的排队时间。

## C. 库存与幂等性核验

独立活动 3：`initial stock = 100`；1000 个不同签名用户以 1000 并发请求，3 秒发压窗口。此轮只用于正确性而非 QPS：客户端创建 1000 个请求本身造成 7–8 秒延迟，900 个库存耗尽拒绝是预期业务结果。

|---|---:|
| 初始 Redis 库存 | 100 |
| Redis 剩余库存 | 0 |
| Redis 参与用户集合大小 | 100 |
| HTTP/Lua 成功预扣数 | 100 |
| MySQL `orders` 最终秒杀订单数 | 100 |
| MySQL 不同用户数 / 不同 requestId 数 | 100 / 100 |
| `SECKILL_ORDER` outbox 已发送 | 100 |

| 同用户重复订单 | 0 |

| Redis 成功预扣但没有最终订单 | 0 |
| 超卖 | 否（100 ≤ 100） |

独立端到端延迟活动 4 也得到 Redis 余量 0、用户集合 100、MySQL 订单 100、不同用户 100、不同 requestId 100、待发送 outbox 0、RabbitMQ 队列 0。因而在两个隔离夹具上，Redis、MQ 投递状态与 MySQL 订单计数均已最终一致。

## 瓶颈判断

1. **应用侧同步路径 + MySQL outbox 写入**：接口在 Lua 成功后同步执行 Redis reservation 状态写和 `local_message` 插入；并发上升时吞吐饱和在约 420–484 QPS，P95/P99 明显恶化。没有独立的 CPU、GC、数据库慢查询指标，因此“应用与 MySQL 交界”是基于曲线和代码的推断，不是单独归因测量。
2. **outbox 发布调度是最终一致性延迟的确定瓶颈**：`@Scheduled(fixedDelay=5000)` 每轮 `findPending(100)`，理论扫描上限约 20 条/秒；这与 5.6–6.9 秒的 100 单端到端结果一致，并会在接口 400+ QPS 时快速积压。
3. **RabbitMQ 不是本轮观察到的队列堆积点**：最终两场一致性活动的秒杀队列均为 0 ready / 0 unacked；但本测试未采集 RabbitMQ 的 CPU、磁盘和 publish-confirm 细分指标，不能据此宣称 MQ 在所有负载下都不是瓶颈。
4. **Redis 未见正确性故障**：Lua 原子库存/资格保护在 1000 用户库存测试中正确限制为 100；但没有 Redis `INFO`、慢日志或 CPU 指标，不能给出 Redis 容量上限。

## 最值得做的三项优化

1. 将 outbox 投递从固定 5 秒、单批 100 改为可配置的高频批量发布/并行 confirm 管道，并保留失败重试与幂等语义；先消除约 20 条/秒的最终下单吞吐上限。
2. 将秒杀 HTTP 路径中的 outbox 持久化成本做专门剖析：采集 Hikari 等待、MySQL 写入耗时、GC 与 Tomcat 线程指标；再决定是否采用批量化、索引调整或独立可靠投递组件，不能只凭 Redis Lua 很快就跳过 MySQL 成本。
3. 让压测客户端、应用、Redis、RabbitMQ、MySQL 分机部署，并增加 Micrometer/Redis/RabbitMQ/MySQL 监控；当前同机结果适合定位趋势，不足以给出生产容量承诺。

## 可写入简历的表述（严格基于本次测量）

> 在 Spring Boot 3 秒杀链路中完成 Redis Lua 库存预扣、MySQL outbox、RabbitMQ 异步订单的同机高并发压测：30 秒稳态测试中接口峰值 484 QPS，按 P99 42 ms 的低尾延迟标准稳定运行约 420 QPS；1000 用户抢 100 库存一致性测试实现 Redis 预扣、MQ 投递、MySQL 订单均为 100，未出现超卖或重复订单。进一步测得端到端订单落库 P99 为 6.91 s，定位 5 秒/100 条 outbox 发布调度为主要异步延迟瓶颈。
