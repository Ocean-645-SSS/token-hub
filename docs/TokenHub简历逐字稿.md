# TokenHub 面试逐字稿（背诵版）

> 使用方法：先背「全局名词表」和每条「背诵卡」，再逐条背六大模块，最后用「防拷打追问」自测。所有话术按当前源码口径，**不夸大、能出示代码与报告**。岗位 JD 侧重点已标注在每条开头。

## 项目定位与商业模式（开场 30 秒背熟）

> TokenHub 是**模型界的携程/虚拟运营商**：面向 AI 应用开发者，卖「指定模型的 Token 额度」，用户走 OpenAI 兼容接口调用，平台在背后路由到真实厂商。

**一句话定位**：这是一个「模型额度交易 + 计费」的**聚合网关**，不是模型厂商。

**两层 API key，别混**：

| 层 | 谁持有 | 作用 |
| --- | --- | --- |
| 下游 key | 用户创建（`th_` 开头，平台签发） | 标识"你是谁、允许调哪些模型" |
| 上游 key | 平台私有（配置里） | OpenAI/DeepSeek/Claude 的真实凭证，用户拿不到 |

**两个独立动作，都绑 `userId`**：

- 买套餐 = 充值额度 → 进 Wallet（按 modelCode 分账）
- 创建 API key = 拿调用凭证 → 带 `allowedModels`

**逻辑模型与上游入口**：用户请求里的 `model` 是模型名（modelCode），平台用 `ProviderRouter` 选择已配置的兼容上游（`provider_code`）。调用过程通常无需用户手动切换，响应可能包含上游模型名。

**计费闭环**：买额度入账 → 调用前冻结 → 按真实 usage 结算 → 失败或用量未知时释放。冻结和结算绑定用户请求的模型；`provider_code` 记录实际供应商，配置的 `unitCost` 用于路由评分，尚未实现实际成本金额核算。

## 简历 bullet（原文）

### 简介
面向 AI 应用开发者的模型额度交易与计费平台，覆盖套餐购买、限时抢购、模型调用及智能导购，重点解决订单异步履约、额度一致性与实际用量结算问题。
### 技术栈
Java、Spring Boot、MyBatis-Plus、MySQL、Redis、Lua、RabbitMQ、Elasticsearch、Docker。
### 额度账户与可靠记账
针对模型调用前实际 Token 消耗量不确定的问题，设计额度预冻结、按上游实际 usage 结算及失败释放流程；通过 Wallet＋Ledger 账户模型、业务幂等标识和数据库唯一约束，保障余额变更与流水记录一致，避免重复记账。
### 双交易链路与订单状态机
针对普通购买与秒杀的并发差异，分别采用 MySQL 事务同步扣库存建单和 Redis Lua 原子预占、MQ 异步建单；结合请求幂等、状态条件更新与库存补偿，处理重复下单及支付、取消、超时竞争。
### Outbox 可靠消息投递
将业务状态变更和本地消息写入同一 MySQL 事务，通过 Publisher 异步投递、消息确认与 Consumer 幂等消费衔接订单履约与额度发放，降低事务提交后但消息丢失造成的业务不一致风险。
### 套餐推荐导购链路
将用户自然语言需求解析为结构化筛选条件，结合参数校验、ES 多条件搜索与候选集约束推荐套餐，并以真实套餐数据校验价格和额度信息，减少模型生成不实商品信息的风险。
### 异步链路压测与优化
针对 Outbox 消息认领和 MQ 消费延迟问题，调整 Publisher 线程池及 Consumer 并发配置；在 100 并发测试中，将消息认领 P99 由 5.229s 降至 1.316s、消费等待 P99 由 3.076s 降至 0.361s，并核验 100 笔成功订单。

## 全局名词速查表（背到条件反射，每条「概念 + 在本项目里的用法」）

| 名词 | 一句话概念 | 在本项目里的用法 |
| --- | --- | --- |
| `requestId` | 一次"受理"的编号，服务端生成返回给客户端，用来后续查进展 | 秒杀入口返回 requestId，用户拿它轮询查订单；模型调用里 `model_request.request_id` 存的是客户端幂等键（Idempotency-Key） |
| `QUEUING` | 秒杀接口返回给用户的"已受理、排队建单中"状态 | 表示抢到资格但订单还没建出来，返回 QUEUING + requestId |
| `SUCCESS:orderNo` | 秒杀结果查询返回"已建单"，带上订单号 | 用户查到它就能去支付 |
| `WAIT_PAY` | MySQL 订单的"待支付"状态 | 建单成功即进入 WAIT_PAY，支付后转 PAID |
| `RESERVED` | 秒杀预占记录的"已占位"状态（表 `seckill_reservation`） | 表示这个资格被占住、等待异步建单 |
| `ORDER_CREATED` | 预占记录的"已建单"状态 | 异步建单完成后写入，对应 SUCCESS |
| `RELEASED` | 预占"已释放"状态 | 取消或补偿后释放，库存回补 |
| `COMPENSATION_PENDING` | 预占"待补偿"状态 | 补偿任务先置此状态，迟到的建单消息看到它就不再建单 |
| Outbox / `local_message` | "发件箱"模式：把"接下来还要做什么"和业务状态写进同一个 MySQL 表，之后再异步投递 | 支付、建单、超时、库存同步等事件都先落 local_message，避免事务提交后消息丢失 |
| Publisher | 应用里扫描 local_message 并投递到 RabbitMQ 的后台组件 | 定时认领→发送→按 confirm 收尾 |
| Broker | 消息中间件服务本身 | 这里指 RabbitMQ |
| Consumer | 订阅队列、执行业务逻辑的监听器 | 如 TokenGrantConsumer、SeckillOrderConsumer |
| confirm | RabbitMQ 对"发布方"的确认，表示 Broker 收到消息 | 只说明消息送达 Broker，**不等于消费完成** |
| ACK | 消费者处理完后的确认，表示业务成功、可不再投递 | Spring AMQP AUTO 在 listener 正常返回后确认 |
| Wallet（`token_wallet`） | 每个用户每个模型的"余额快照" | 含 `available_token`、`frozen_token`、`credit_limit` |
| Ledger（`token_ledger`） | 余额的"变更流水" | 每次入账/扣费的明细，带 `bizId` 唯一标识 |
| `model_request` | 一次模型调用的记录 | 存状态、预冻结量、真实 usage、重试次数、结果引用 |
| 预冻结（freeze） | 调用前先按估算占用额度，防止并发超用 | 只是"占用"，**不是实际扣费** |
| `usage` | 上游返回的真实 Token 消耗量 | `prompt + completion = total`，是最终扣费依据 |
| `Idempotency-Key` | 模型调用的幂等键，回答"这是哪一次请求" | 同键重试返回已存结果，不重复扣费 |
| `purchaseKey` | 普通购买的幂等键 | 同用户同键只建一单 |
| `prefetch` | 每个消费者能同时持有的"未确认消息"上限 | 不是一次必取的数量，也不是业务线程数 |
| `catalog_version` / external version | ES 写入时带的业务版本号 | 旧版本不能覆盖新版本 |
| tombstone | 下架套餐在 ES 保留 `active=false` 的文档（带版本） | 防止旧消息把已下架商品"复活" |
| DLQ | 死信队列，重试耗尽的消息进这里 | 便于排查和重放 |
| `ModelProvider` 接口 | 统一的上游调用契约：`complete(请求)→ProviderResponse` | 每个厂商一个 adapter 实现它，屏蔽协议差异 |
| adapter（适配器） | 把统一请求翻译成某家厂商原生协议、再把响应翻译回来 | OpenAI/DeepSeek 共用一个，Claude 单独写一个 |
| `HttpModelProvider` | 共享基类：HTTP、超时、错误码→`retryable` 映射 | adapter 只写协议翻译，不重复写网络逻辑 |
| `ProviderRegistry` | 从配置构建 Provider 候选列表 | 按 `type` 用工厂 new 对应 adapter |
| `ProviderRouter` | 路由：先筛模型能力，再按成本 + 延迟 + 熔断状态给候选排序 | 排除不支持模型或 OPEN 的候选，返回最优到次优 |
| `CircuitBreaker` | 熔断器：连续失败到阈值就熔断、冷却后放探活 | 每 Provider 一个，独立记成功/失败 |
| `CLOSED/OPEN/HALF_OPEN` | 熔断三态：正常 / 熔断 / 半开探活 | HALF_OPEN 只放一个请求，成功回 CLOSED、失败回 OPEN |
| `failover`（故障切换） | 允许切换的错误发生时，按序尝试下一个兼容 Provider | 读取超时等结果未知的情况停止切换 |
| `unitCost` | 配置的 Provider 单位成本 | 用于路由打分，不直接用于用户计费 |
| 延迟 EMA | 成功调用耗时的指数滑动平均 | 路由的"延迟"维度，低者优先 |
| `type`（provider 类型） | 配置里标记厂商协议：`openai` / `anthropic` | 工厂据此选 adapter；DeepSeek 用 `openai` |
| `provider_code` | 记录本次调用最终服务的 Provider | 落在 `model_request`，支撑成本分析 |
| `usage` 归一 | 把各家不同的用量字段统一成 `totalTokens` | Claude 用 `input+output` 加出来，缺了走 BILLING_UNKNOWN |

# 第一条｜普通购买 vs 秒杀：建单前分道，建单后合流

> **JD 定位**：主打「高并发 + 一致性」，对应 JD 能力要求里的"高并发经验优先"。

## 🎯 背诵卡

- **一句话**：普通购买是"先建单 → 再支付 → MQ 发额度"；秒杀是"先抢资格 → MQ 建单 → 再支付 → MQ 发额度"。
- **核心差异**：两条链路**只在建单前不一样**，建单后的支付、发放、超时、回补**完全共用**。
- **三个锚点**：普通 = MySQL 事务同步建单；秒杀 = Redis Lua 预筛 + MySQL 预占 + MQ 异步建单；防重复 = 数据库唯一键。
- **必背名词**：`WAIT_PAY`（待支付）、`QUEUING`（排队受理）、`RESERVED → ORDER_CREATED → RELEASED`。

## 一、背景（为什么会有两条链路）

> 我们卖的是"指定模型的 Token 额度"。平时买套餐，用户希望点下去**立刻**看到一张待支付订单；秒杀不一样，活动一开始请求瞬间涌进来，这时候最重要的不是马上建单，而是**先判断这个人有没有抢到资格**，再让后台按自己的节奏慢慢建单。所以两条入口的差别，我集中放在**建单之前**，后面该支付、该发额度都一样。

## 二、做了什么（一句话说清方案）

> 普通购买做成**同步建单**；秒杀拆成 **Redis 预筛 → MySQL 确认预占 → MQ 异步建单** 三段。两条链路建完单之后，共用模拟支付、超时关闭和额度发放。

## 三、怎么分步做的（三步，每步记一个关键词）

**第一步：普通购买 = 一个 MySQL 事务搞定。**
在同一事务里做三件事：① 插入一张 `WAIT_PAY`（待支付）订单；② 带 `stock > 0` 条件扣库存，影响行数不是 1 就抛异常、整笔回滚；③ 写一条 `ORDER_TIMEOUT` 超时事件。防重复靠 `userId + purchaseKey` 的唯一约束——同一用户带相同购买键重试，只落一张订单，重复请求查回原来的结果。

**第二步：秒杀 = Redis 一个 Lua 脚本 + MySQL 一个事务。**
先用 Redis Lua 一次性完成：校验活动存在、在有效期内、该用户没参与过、库存还够，满足就库存减一、把用户写进参与集合。通过之后，在 MySQL 同一个事务里写三样：预占记录 `seckill_reservation`（`request_id` 唯一 + `user_id + activity_id` 唯一）、扣减 `seckill_inventory.available_stock`、写建单 Outbox。**事务提交后**才返回 `QUEUING` 和 `requestId`（受理号，用户拿它查进展）。

**第三步：异步建单 = Publisher 发 MQ，消费者锁预占记录建单。**
消费者先 `SELECT FOR UPDATE` 锁住这条 `RESERVED`（已占位）预占记录，确认它还能建单，再在同一事务里建 `WAIT_PAY` 订单、写超时事件、把预占推进到 `ORDER_CREATED`（已建单）。用户拿 `requestId` 轮询，查到订单号就能去支付；支付后走和普通购买同一条发放链路。

## 四、成果（说得出、也守得住边界）

> 普通购买**直接返回待支付订单**；秒杀入口**先给一个能查的受理结果**，而不是让用户在原地干等。关键一点：预占记录落进了 MySQL，就算 Redis 的查询结果键丢了，用户照样能查到进展。重复建单和重复回补，靠数据库唯一键 + 状态条件迁移一起挡住。

## 五、困难（一个真实的冲突，讲"冲突 → 解决"）

> 最难的是**建单和补偿同时发生**。比如建单消息在 MQ 里积压了，恢复任务一看"超时没建单"就准备释放库存，结果原来的消息刚好这时候送到——如果两边各看各的缓存，就会一边释放库存、一边又建出订单。
>
> 我的解法是让**建单和补偿锁同一条预占记录**：补偿先把它推进到 `COMPENSATION_PENDING`（待补偿），迟到的建单消息看到这个状态就**不再建单**；释放库存和写同步事件在同一个事务提交，Redis 按版本号同步"绝对可用量"，重复投递也不会给库存多加一份。

## 六、下次优化

> 下次我会先压单场活动，看 MySQL 那行库存记录在什么负载下开始出现**锁等待**，再决定要不要按配额分片。验证时我会专门测三个场景：**最后一份库存竞争、消息迟到、进程重启**，核对可用库存、有效预占和订单三者能不能对得上。

## 七、防拷打追问（每题背 1–2 句）

1. **普通购买已经用了事务，为什么还要 MQ？**
   事务保证"当前这批数据库操作"一起成功一起失败；MQ 解决"后续工作异步执行"（发放、超时、回补）。两个是不同层面的东西，不冲突。

2. **两个请求同时先查到"没有订单"怎么办？**
   让**数据库唯一键裁决**。重复插入的一方事务回滚，外层再查胜出的那笔订单返回。不能只依赖先查一遍。

3. **Redis Lua 原子做了什么？为什么不用 GET 再 DECR？**
   Lua 把"检查 + 扣减"放进同一个脚本执行，避免"检查时还有货、扣减时被被人抢走"；`GET` 和 `DECR` 两条命令之间会被别的请求插进来。

4. **秒杀支付时还会再扣一次 MySQL 库存吗？**
   不会。秒杀库存是活动前预热到 Redis、实时在 Redis 预扣，跟普通套餐库存是**两份独立库存**，不能拿同一份扣两次。

5. **QUEUING / SENT / WAIT_PAY 是同一个状态机吗？**
   不是，先说清它属于谁：`QUEUING` 是客户端看到的秒杀受理结果，`SENT` 是 Outbox 消息的发送状态，`WAIT_PAY` 是 MySQL 订单的业务状态。

6. **回补库存后，这个用户能重新抢吗？**
   不能。库存占用和参与资格是分开的，释放的那一份给**别的没参与过的用户**，不恢复原用户的参与资格。

# 第二条｜Token 账户与计费：买进来 vs 花出去，各管各的幂等

> **JD 定位**：这是**整份简历的主角**，直接命中 JD 的「计费与配额体系」（Token 计量、计费、配额管理）。面试官在这个方向追问最密，多讲配额（`credit_limit`）、按真实 usage 结算、幂等。

## 🎯 背诵卡

- **一句话**：买额度是"支付 → MQ 发额度"，花额度是"冻结 → 按真实 usage 结算 → 失败释放"。
- **三张表**：Wallet（余额快照）、Ledger（变更流水）、model_request（一次调用记录）。
- **两个幂等**：购买用订单号（`TOKEN_GRANT_ORDER_订单号`），调用用请求号（`Idempotency-Key`）。
- **必背数字**：中文约 1.8 字 / Token、英文约 0.75 词 / Token，标点等按字符粗估；默认授信 0；明确连接失败最多尝试 3 次，退避 200ms/500ms。

## 一、背景（问题在哪）

> 用户买的额度是**按模型分开存**的。但一次模型调用真正消耗多少，要等上游返回 `usage`（真实 Token 用量）才知道。如果并发请求都只查一下可用余额就放行，它们会同时用到同一份额度。另一方面，购买发放是异步的，消息重投可能重复加钱。所以发放和消费**两条路都要处理重复执行**。

## 二、做了什么（一句话说清方案）

> 把账务拆成**钱包（余额）、流水（明细）、调用记录**三层。购买侧用订单号做发放幂等；调用侧先冻结，成功后按真实 `usage` 结算，最终失败释放冻结。

## 三、怎么分步做的（三步）

**第一步：购买入账 = 锁钱包 + 唯一流水，防重复加钱。**
模拟支付在同一个事务里把订单改成 PAID、写 `TOKEN_GRANT` Outbox。发放消费者 `SELECT FOR UPDATE` 锁住对应钱包，用订单号拼出唯一流水标识（`TOKEN_GRANT_ORDER_订单号`），只有 `insertIgnore` 返回 1（第一次插入成功）才给余额加额度，再推进订单状态。两步在**同一事务**，不会出现"流水提交了、余额没加"的部分成功。

**第二步：调用前 = 幂等登记 + 预冻结（同一 MySQL 事务）。**
先用请求头 `Idempotency-Key`（幂等键，回答"这是哪一次请求"）登记：同一个键如果已有成功结果，直接返回存的结果，不再调上游。新请求按"估算输入 + maxOutputTokens + 安全余量"算出预冻结量。输入文本按中文、英文和其他字符分别粗估，在**同一个 MySQL 事务**里完成"插入调用记录占位 + 锁钱包 + 冻结额度"，再调上游。

**第三步：调用后 = 按真实用量结算或释放。**
上游成功返回 `usage` 后，在**同一个事务**里推进请求状态、更新钱包余额、写消费流水——三者一起提交或回滚，不存在"余额改了流水没记"的部分成功；最终失败就释放全部冻结。上游返回成功但缺 `usage` 时，调用记录标 `BILLING_UNKNOWN`、释放冻结，保留"这次计费未知"的状态，**不拿估算值收费**。

## 四、成果（收益）

> 这套流程把"买到的额度"和"用掉的额度"串成了闭环。购买重投时，唯一流水和钱包更新在同一事务里，重复消息不会再次发放。调用侧有请求去重和预冻结，成功扣多少由上游 `usage` 决定，账上可以靠调用记录和消费流水追到这笔额度，配额（`credit_limit`）也在冻结检查时生效。

## 五、困难（讲真实的实现边界，别吹成"绝对安全"）

> 难点是**请求去重和账务幂等是两层，得分开处理**：请求去重保护的是"别重复调用上游"，账务幂等保护的是"一笔真实消耗只生效一次"。结算代码曾经有两个短板——self-invocation 导致事务不生效、先改余额后插流水却没检查插入结果；我把结算收敛到一个 `@Transactional` 方法里，让"请求状态 + 钱包余额 + 消费流水"在同一个数据库事务里提交或回滚，并写了回归测试验证：流水写入失败时余额会回滚、重复结算只扣一次。

## 六、下次优化

> 结算事务性已经收敛（请求状态、钱包、流水同事务提交/回滚，回归测试覆盖重复结算与流水失败回滚）。下一步我会补故障注入测试，验证提交前后进程退出时钱包和流水能否恢复到一致，并把配额（`credit_limit`）超用后暂停账户的边界用例再覆盖一遍。

## 七、防拷打追问（这组是 JD 主战场，务必背熟）

1. **Wallet / Ledger / model_request 三张表分别做什么？**
   Wallet 是每个用户每个模型的**余额快照**（可用、冻结、信用额度）；Ledger 是**变更流水**（每次入账/扣费明细，带唯一 bizId）；model_request 是**一次调用的记录**（状态、预冻结量、真实 usage、重试次数）。

2. **冻结 2000 就写一条消费 2000 的流水吗？**
   不写。冻结只是**占用**额度，真实消费要等上游 usage。如果实际用 1500，最终消费流水是 -1500，多冻结的 500 释放。

3. **为什么先插流水、再改钱包？**
   先通过唯一流水判断"这次是不是第一次产生业务效果"，只有首次插入才更新钱包；两步在**同一事务**，不会出现流水提交了、余额没提交的部分成功。

4. **SELECT FOR UPDATE 到底锁什么？**
   按 `(user_id, model_code)` 唯一条件查钱包并加锁，在有效事务里锁住这条钱包记录直到提交，避免并发读出旧余额后互相覆盖；不同钱包互不影响。

5. **给一个预冻结的数字例子。**
   原可用 10000、冻结 0；预冻结 2000 后可用 8000、冻结 2000。实际用 1500，结算后可用 8500、冻结 0，写消费 -1500。彻底失败就恢复可用 10000。

6. **实际 usage 超过冻结量怎么办？**
   默认授信为 0，预冻结所需额度超过可用余额时拒绝新请求。已发出的请求按真实 usage 结算，若超出冻结量导致余额为负，负余额留在该模型钱包；购买同模型套餐到账后先抵扣负余额，足够覆盖下一次冻结时可继续调用。其他模型钱包不受影响。

7. **客户端超时，但服务器其实已经结算成功怎么办？**
   客户端重试复用原 `Idempotency-Key`，查到 SUCCESS 就返回原结果，**不再调用也不再扣费**。计费成功不以客户端有没有收到 HTTP 响应为准。

8. **三次重试会扣用户三次吗？**
   不会。计费目标是"一项业务请求只记一次成功结算的消费"；失败尝试的上游成本由平台承担，不每次失败都扣用户。

# 第三条｜Elasticsearch 套餐搜索 + AI 导购：模型输出必须回到业务事实

> **JD 定位**：弱匹配，**降级处理、别占太多时间**。它更像"帮用户选套餐/模型"，可轻带一句"数据洞察"但别吹成分析平台。核心价值是展示"怎么约束 LLM 输出、防幻觉"。

## 🎯 背诵卡

- **一句话**：两阶段导购——先让 LLM 把自然语言转成结构化条件，后端校验后查 ES，再让 LLM 基于**真实候选**写推荐理由。
- **一个原则**：价格、库存、可售状态由**业务系统**控制，LLM 只负责"理解需求 + 写文案"，不能编商品、不能写 SQL。
- **三个兜底**：解析失败回退关键词 + 预算；推荐失败走模板；空候选明确说"暂无"。

## 一、背景（问题在哪）

> 用户选套餐时可能只说"预算有限，想买平时写代码用的额度"。这句话里有用途和预算，但搜索接口需要明确的关键词和筛选条件。而且推荐结果里出现的套餐和价格，**必须能在当前商品目录里查到**——不能让模型编一个不存在的套餐或价格出来。

## 二、做了什么（一句话说清方案）

> 导购拆成**两次模型调用**：第一次把自然语言转成结构化筛选条件，后端校验后查 ES；第二次把查到的**真实套餐**交给模型，让它解释每个候选为什么合适。MySQL 保存套餐事实，ES 只是搜索投影。

## 三、怎么分步做的（三步）

**第一步：约束模型只返回约定字段，后端做两层校验。**
后端检查字段类型、价格和 Token 数量的范围，也检查指定的 `modelCode` 在 MySQL 里有没有**在售套餐**——格式合法 ≠ 业务合法。遇到需要用户澄清的条件，先返回澄清问题，不擅自替用户发明预算。

**第二步：ES 多条件搜索 + 索引同步。**
用关键词查套餐名称和描述，再叠加模型、价格、Token 数量和上架状态过滤。后台改套餐时，同一个 MySQL 事务会写 `PACKAGE_INDEX_SYNC` 事件；消费者**重新读 MySQL 当前事实**写 ES，用 `catalog_version`（业务版本号）做 external version 挡住旧写，下架套餐保留带版本的 tombstone（`active=false` 文档），避免旧消息把商品复活。

**第三步：基于候选生成推荐理由，层层兜底。**
把检索到的候选交给模型生成理由。意图解析重试后仍失败，回退到原始关键词 + 显式预算；推荐生成失败，用候选事实生成模板说明；候选为空，直接告诉用户"暂无符合条件的套餐"。

## 四、成果（收益）

> 用户能用自然语言表达需求，后端仍按明确条件过滤，推荐能落到**实际在售套餐**上。套餐修改和下架通过同步事件更新索引，版本控制挡住旧写入，60 秒一次的全量对账修复索引偏差。用户真正下单时，再回 MySQL 按当前套餐状态校验——ES 只负责"搜得到"，不负责"成交"。

## 五、困难（两个容易被忽略的坑）

> 一个坑是模型返回的 JSON **格式正确、意思却不对**——比如编码看起来合法，但目录里根本没有这个在售模型。另一个坑是**下架后消息乱序**：如果直接删掉搜索文档，迟到的旧写入可能把套餐重新放回搜索结果。前一个靠业务校验解决，后一个靠版本号 + tombstone 解决。

## 六、下次优化

> 我会先整理一组**可重复跑的导购样例**，覆盖预算上限、模型别名、条件冲突、空结果、刚下架的套餐。每条样例都检查"解析出来的条件、召回的套餐、最终的理由"，这样换提示词或换模型时，能判断变化到底出在**意图解析、搜索、还是推荐生成**哪一层。

## 七、防拷打追问（每题背 1–2 句）

1. **为什么不让 LLM 直接选套餐或写 SQL？**
   价格、库存、可售状态必须由业务系统控制。结构化条件便于校验、ES 候选提供事实范围，模型负责理解需求和写文案，后端负责可信约束。

2. **LLM 输出了合法 JSON，就能直接查 ES 吗？**
   还不够。格式合法与业务合法是两层：还要校验字段、数值范围、预算，并查指定 `modelCode` 是否有在售套餐。

3. **模型编了一个格式正确但不存在的 modelCode 怎么办？**
   当前已补 MySQL 在售套餐校验，找不到就返回澄清并暂停检索，**不静默把 modelCode 设成 null 放宽搜索**。

4. **为什么消费时读 MySQL 最新数据，而不是信旧消息里的套餐？**
   消息可能积压或乱序，读当前事实能减少把历史快照写回的风险；版本保护仍保留，防止两个消费者读到不同版本再逆序完成。

5. **external version / tombstone / DLQ 各解决什么？**
   external version 用业务版本拒绝旧写覆盖新写；tombstone 是带版本的 `active=false` 文档，表示已下架、防止旧消息复活商品；DLQ 保存重试耗尽的消息，便于排查和重放。

6. **MySQL 有套餐但 ES 搜不到怎么办？**
   先区分"没有匹配候选"和"交易时套餐已失效"。空候选不编造推荐，保留用户条件提示暂无、等待同步；下单回 MySQL 校验是另一层交易保护。

7. **套餐本身是怎么设计的？核心字段有哪些？**
   套餐本质是「某个模型的 token 额度包」，核心三元组是 `modelCode`（绑模型，决定额度进哪个钱包账户）、`tokenAmount`（含多少 token）、`price`（价格）。检索辅助 `description` + `suitableScenario`（场景标签）给 ES/AI 导购召回；交易控制 `stock` + `status`。动机两点：额度按「用户 + 模型」分账必须绑 modelCode；场景标签让"我要写代码"能被召回。买套餐只充值额度，调用还要另建 API key（带 `allowedModels`）。

# 第四条｜秒杀链路压测与性能优化：从"入口快"到"订单落地快"

> **JD 定位**：主打「稳定性与可观测性」——用 requestId 分段打点定位瓶颈，配合限流、重试退避，正好命中 JD 的"限流、熔断、重试 + 日志监控告警"。

## 🎯 背诵卡

- **一句话**：秒杀接口十几毫秒就返回 QUEUING，但订单落地慢——我不用入口耗时当指标，而是从受理一路跟踪到建单成功，找出后台时间花在哪。
- **两段瓶颈 + 两个改动**：Publisher 领取慢 → 发消息移到有界线程池；Consumer 排队慢 → 加消费者 + 降 prefetch。
- **必背数字**：Publisher 轮 `5.229s → 1.316s`（Outbox 插入消息到Publisher领取）；Consumer 轮 `3.076s → 0.361s`（RabbitMQ confirm 到Consumer开始处理）。
- **一句话守边界**：100 并发 ≠ 100 QPS；100 单建单成功 ≠ 100 单支付到账。

## 一、背景（问题在哪）

> 当时秒杀接口很快就返回了 QUEUING，但用户还要等一段时间才能查到待支付订单。如果只看入口接口的耗时，就看不到这段等待。所以我把压测目标定成**从秒杀受理跟踪到订单创建成功**，找出后台时间具体花在哪。

## 二、做了什么（一句话说清方案）

> 用 `requestId` 串起服务端各阶段打点，测出两段主要等待：第一段在 Outbox 插入之后、Publisher 领取之前；第二段在 RabbitMQ 确认之后、监听器入口之前。分两轮调整，先改 Publisher，再改秒杀队列的消费配置。

## 三、怎么分步做的（三步）

**第一步：打点定位，先看消息卡在哪。**
记录 Outbox 插入、Publisher 领取、Broker confirm、监听器入口、建单完成五个时间点，对每个请求分别算各段耗时，再统计 P99。发现进入监听器后的业务处理比前两段等待短得多，所以先看消息是怎么排队的。

**第二步：改 Publisher —— 把发送和扫描拆开。**
把消息发送移到有界线程池（core=4 / max=8 / queue=500），调度线程只负责查询、认领和派发，发送结果仍通过 confirm 回调收尾。这样扫描和发送各自推进，不会因为一批消息逐条发送把后面的领取拖住。

**第三步：改 Consumer —— 加并发 + 降 prefetch。**
给秒杀建单队列单独配监听容器，消费者从 1 个调到 4–8 个，prefetch（每个消费者可持有的未确认消息上限）从 250 调到 32。更多消费者并行处理独立订单，较小的 prefetch 减少消息集中压在单个消费者手里的情况。

## 四、成果（收益 + 数字口径）

> 在当时的压测版本中：Publisher 优化这一轮，Outbox 插入到领取的 P99 从 **5.229 秒降到 1.316 秒**；随后调消费配置，confirm 到监听入口的 P99 从 **3.076 秒降到 0.361 秒**。正式样本负载窗口 5 秒、并发数和库存都是 100，100 个受理请求最终都建成了待支付订单，也核对了库存和重复订单（distinct user 和 requestId 都是 100）。注意这组数字对应的是改造前的版本，后来秒杀入口加了 MySQL 持久化预占，口径要分开说。

## 五、困难（真实坑：指标好了，客户端没同步变好）

> 最难的是**服务端分段指标改善了，客户端看到的耗时却没有同步改善**。我回头查压测代码，发现它会**先等整批 POST 全部结束，再统一开始轮询结果**——较早完成的请求也要等其他 POST，这段等待被算进了单请求的客户端耗时（实测 POST 响应到首个 poll 平均约 4.86 秒，而 Result API 服务端 P99 只有约 4.4 毫秒）。所以这次我用对应轮次的服务端分段数据说明优化效果，不把这个带批次屏障的数当成绩宣传。

## 六、下次优化

> 我会让每个请求拿到 `requestId` 后就**按各自的时间独立开始轮询**，不等整批 POST；同时分别记录入口响应、服务端建单完成、客户端观察到成功三个时间。然后给现在这版持久化预占重跑基线，逐级提高负载，结合库存行锁等待、Outbox 积压、队列积压，判断新的瓶颈在哪。

## 七、防拷打追问（每题背 1–2 句）

1. **100 并发就是每秒 100 单吗？**
   不是。100 是"同时在推进的请求数"，不是 QPS（每秒请求数）。每单耗时、等待、脚本循环模式都影响最终吞吐，HTTP 吞吐也不等于成功订单吞吐。

2. **100/100 完成是支付到账成功吗？**
   不是。这条性能链路的终点是"秒杀异步建单成功 + 结果更新"，**不包含后续支付和 Token 发放**。口述时要明确说"受理请求最终正确建单"。

3. **P99 是最慢的那一笔吗？**
   不是。P99 是排序后的百分位边界，不天然等于最大值；只有 100 个样本时 P99 接近样本尾部、波动大，适合阶段定位和复测，不能推成生产容量承诺。

4. **ready=0 就说明 MQ 没积压吗？**
   不能。消息可能已经预取到 Consumer 侧、处于 unacked 状态。要结合监听入口延迟才能判断是否在消费者侧等待，单个瞬时指标不够。

5. **为什么判断慢在 Publisher/Consumer 而不是 MySQL？**
   当轮样本里 Outbox 领取和 confirm→listener 是秒级等待，而进入 listener 后的业务阶段远短于这两段（业务事务 P99 只有几十毫秒），证据指向消息等待。

6. **Publisher 已经 200ms 轮询，为什么还能等 5 秒？**
   fixedDelay 是"上一轮结束后再等 200ms"，不是每 200ms 强制开新轮；单 scheduler 要逐条推进一批消息，一轮本身可能持续数秒，后来的事件还得等。

7. **为什么同时降低 prefetch？**
   减少单个 Consumer 提前占住大量未确认消息的情况；但也不是越小越好、消费者越多越好——过多消费者会争抢数据库连接和锁（本轮已经出现 Hikari 等待信号），要结合观测调。

8. **为什么服务端快了，客户端 E2E 还是约 5.4 秒？**
   是压测客户端的**批次屏障**：它先等整批 POST 结束再统一轮询，早完成的请求在等其他 POST，这段等待被算进单笔 E2E。不是纯单请求的完成体验。

# 第五条｜多模型统一接入 + 路由 + 熔断：把"单点直连"升级成"网关"

> **JD 定位**：直接命中 JD 任务 1（多模型统一接入）、2（智能路由/故障切换）、5（成本分析），是这份简历对 JD 的**最强补充**，也是你区别于"只会写 CRUD"的地方。这条务必讲透。

## 🎯 背诵卡

- **一句话**：把"单 Provider 直连"升级成"统一契约 + 多厂商 adapter + 成本/延迟/熔断路由 + 故障自动切换"。
- **三个锚点**：① adapter 统一契约（屏蔽协议差异）② Router 按成本+延迟+熔断打分排序 ③ CircuitBreaker 三态 + failover。
- **必背名词**：`ModelProvider`（统一接口）、`ProviderRouter`（路由）、`CircuitBreaker`（熔断）、`CLOSED/OPEN/HALF_OPEN`、`usage` 归一、`provider_code`。
- **一句话守边界**：切换发生在 Provider 层；冻结和结算绑在请求的模型上，响应可能暴露上游模型名。

## 一、背景

> 原来的模型调用只有一个 OpenAI-compatible 端点，用户请求什么模型就直连发过去，没有"多厂商"概念，也没有故障兜底——某个上游一挂，请求就失败。而且不同厂商协议根本不一样：Claude 的请求要把 system 拆出来、usage 只给 input/output 没有 total。JD 要的"统一接入 + 智能路由 + 故障切换"，本质就是把这些差异藏起来。

## 二、做了什么

> 我用**适配器模式**：统一契约就是 `ModelProvider` 接口 + OpenAI 形状的请求/响应，由 adapter 做双向翻译；再在它前面加一层 `ProviderRouter`，筛选模型和熔断状态后按成本、延迟排序，每个 Provider 有独立的三态熔断器。遇到允许切换的错误，才尝试下一个兼容入口。

## 三、怎么分步做的（四步）

**第一步：定统一契约 + 写 adapter。**
`ModelProvider.complete(ChatCompletionRequest) → ProviderResponse`，输入输出都是 OpenAI 形状。OpenAI/DeepSeek 一个 adapter 直通；Claude 单独写一个，做完整消息转换：合并多条 system/developer 消息为独立字段、把图片转成 Anthropic 的 image 块、把函数工具调用及结果转成 tool_use/tool_result，并把 usage 归一成 `totalTokens`（Claude 只有 `input_tokens + output_tokens`，要自己加）。缺省 `max_tokens` 设为 1024，受网关输出上限约束。

**第二步：抽基类 + 工厂。**
`HttpModelProvider` 放 HTTP 调用、超时、以及"各家错误码 → retryable"的统一映射；adapter 只写协议翻译。`ProviderAdapterFactory` 按配置里的 `type`（`openai`/`anthropic`）new 对应 adapter——DeepSeek 走 `openai` 类型，零新代码。

**第三步：注册表 + 路由 + 熔断。**
`ProviderRegistry` 从配置构建候选列表；`ProviderRouter` 先按 Provider 的 `models` 映射筛掉不支持该模型的候选，再按「成本单价 + 延迟 EMA」打分排序（Anthropic 需要显式映射，未配置映射的 OpenAI 兼容供应商继续透传模型名）；每个 Provider 一个 `CircuitBreaker`，`CLOSED → OPEN → HALF_OPEN → CLOSED`，连续失败到阈值就熔断、冷却结束后重新进入候选列表，同一时间只放一个半开探测，探测成功才恢复流量。

**第四步：调用循环改成 failover。**
`ChatCompletionService` 按路由顺序尝试候选，错误分三类处理：明确的连接失败在单 Provider 内有限重试（退避）；明确的限流或过载（429/529）不重试、直接记熔断失败并切下一个；读取超时和结果不明的 5xx（含 503）**停止重试和切换**，释放冻结额度、记 `BILLING_UNKNOWN` 和供应商信息供对账。普通请求拒绝（4xx 客户端错误）不计入熔断。成功就把 `provider_code` 写进 `model_request`。冻结和结算**完全没动**，还绑在用户请求的模型上。

## 四、成果

> 平台具备配置多个上游的能力。存在兼容备用入口且错误允许切换时，可以按候选顺序尝试；超时和结果不明的 5xx 停止切换，记为 `BILLING_UNKNOWN`。当前默认只配置一个本地 mock，客户端可能从上游响应的模型字段看出实际模型名。`provider_code` 和用量供后续成本核算，目前未自动计算成本金额。

## 五、困难

> 三个坑：① **usage 归一化**——Claude 没有 `total_tokens`，我用 `input + output` 加出来，否则不同厂商扣费口径不一致；② **复杂消息转换**——OpenAI 里 system 是 `messages[0]`，Claude 要拆成独立字段并合并多条 system，图片和函数工具调用也要换成 Anthropic 的 image/tool_use/tool_result 块，翻译错就把 system 变成普通对话、工具调用对不上；③ **错误码分类**——各家错误码不同（Claude 的 529 过载、503 结果不明），要统一映射成"重试 / 切换 / 结果不明"三档，才能复用"重试 → 熔断 → failover"这套逻辑而不误触发熔断。

## 六、下次优化

> 我会把熔断从"连续失败阈值"升级成"滑动窗口失败率"（更抗偶发抖动）；再补 SSE 流式的多厂商适配（各家流式协议差异比非流式大得多）。

## 七、防拷打追问

1. **为什么用适配器模式，不把厂商差异 if/else 写在一个类里？**
   每个厂商一个 adapter 只对自己的协议负责，新增厂商只加类、不改老代码（开闭原则）；if/else 会让一个类膨胀，测试和上线互相牵连。

2. **内部统一协议为什么选 OpenAI 形状，不自创一套？**
   对外暴露的就是 OpenAI 兼容的 `/v1/chat/completions`，且 DeepSeek、vLLM 等一大片厂商原生就是这形状——选它翻译成本最低，客户端零改动。

3. **Claude 的 usage 没有 total_tokens，怎么归一？**
   `total = input_tokens + output_tokens`，在 adapter 里算好再进统一 `ProviderResponse`；缺任何一个就置 null，走已有的 `BILLING_UNKNOWN` 分支，不拿估算值收费。

4. **DeepSeek 接入要写新代码吗？**
   不用。它原生 OpenAI 兼容，配置里加一条 `type: openai` + 换 baseUrl/apiKey 就行。

5. **熔断三态分别什么意思？HALF_OPEN 为什么只放一个请求？**
   CLOSED 正常放行；连续失败到阈值转 OPEN，直接快速失败不傻等、也从路由候选里被排除；冷却期结束转 HALF_OPEN，重新进入候选、同一时间只放一个探活请求——成功回 CLOSED、失败回 OPEN。只放一个是避免刚恢复就被流量打垮。

6. **路由先看什么，再按什么排序？**
   先按 Provider 的 `models` 映射筛掉不支持该模型的候选，再按「成本单价 + 延迟 EMA」两个维度加权排序，低者优先；权重是配置项，当前演示等权，生产要按业务校准。可用性由熔断状态直接排除，不参与打分。

7. **切换发生时，冻结和计费会乱吗？**
   冻结和结算绑定用户请求的模型，成功后按最终响应的真实 usage 扣该模型钱包。请求记录保存实际 `provider_code`，`unitCost` 用于路由评分；平台尚未实现按供应商计算实际成本金额。

8. **哪些错误会重试、切换、熔断？**
   明确的连接失败在同 Provider 内有限重试；限流/过载（429/529）不重试、直接记熔断并切换；读取超时和结果不明的 5xx（含 503）停止重试和切换、释放冻结并记 `BILLING_UNKNOWN`；普通 4xx 请求拒绝不重试、不切换、不计入熔断。重试管"瞬时抖动"，熔断管"持续故障"。

9. **用户怎么管理 API Key？怎么关联模型？**
   不同应用可以各建一把 Key，创建时自定义名称和 `allowedModels`。数据库的 `api_key` 表保存归属用户、名称、前缀、哈希、允许模型、状态和使用时间。明文只在创建时返回。Key 创建后立即可用，也可以撤销。额度按用户和模型记账，同一个用户的多个 Key 调同一个模型时共用钱包。

10. **调用时怎么选模型、按什么计费？**
   创建 Key 时，所选模型必须已有该用户的套餐购买到账流水，余额为零仍可添加。调用时用户在 `body` 的 `model` 字段指定模型，平台校验 Key 权限，再按「用户 + modelCode」检查额度并冻结；成功后按上游实际总 Token 用量结算。

11. **切换上游时，会不会造成效果损失？**
   切换的是厂商不是模型，用户请求的 model 名不变；靠 `models` 映射把逻辑模型翻译成每家厂商的物理模型（Anthropic 必须显式映射，OpenAI 兼容厂商透传模型名）。但客观上不同厂商对"等价模型"的质量有差异——failover 优先保可用，效果一致性是映射配置的责任；严格做法是只在语义等价组内 failover，这是后续优化点。

12. **技术亮点｜为什么把按 Key 的固定窗口换成令牌桶？**
   **问题背景和技术方案可以连起来讲。**
   固定窗口快结束时打满一次，窗口重置后又能立刻打满一次，短时间就可能放行两批流量。现在按 API Key ID 在 Redis 里存一只桶，默认最多放 5 个令牌，每秒补 5 个。模型接口鉴权后，每次请求消耗 1 个令牌，桶空就返回 `429 RATE_LIMIT_EXCEEDED`。Lua 用 Redis 的时间计算补充量，把读余额、补充和扣减放在一次原子操作里，多个应用实例共用同一个桶。这里限制的是请求频率，模型用掉的 Token 仍由钱包结算。

13. **用户怎么知道哪把 Key 用掉了多少 Token？**
   每条 `model_request` 都关联 `api_key_id`。用户用登录 JWT 调 `GET /api/api-keys/{id}/usage`，只能查自己的 Key。调用次数按最近 7 天创建的请求记录计数，上游重试、切换及同幂等键重放都沿用同一条记录。Token 只汇总其中成功结算的用量，失败和计费未知的请求会计入调用次数。Key 撤销后仍能查这段历史。
